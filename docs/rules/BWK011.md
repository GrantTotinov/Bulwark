# BWK011: Forwarded headers are accepted from any proxy

| | |
|---|---|
| Category | Security |
| Severity | Warning |
| Weakness | [CWE-348](https://cwe.mitre.org/data/definitions/348.html): Use of less trusted source |

## Cause

On the same `ForwardedHeadersOptions`, the app calls `KnownProxies.Clear()` and also `KnownNetworks.Clear()` or `KnownIPNetworks.Clear()`.

Clearing only one list is not reported: the other still trusts only loopback.

## Why it matters

The forwarded headers middleware replaces the client IP, scheme and host with the values from `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`, but only for requests from trusted proxies. With both lists empty, every client is a trusted proxy. Any caller can then:

- pick their IP address, which defeats IP rate limits, allow lists, lockouts and audit logs;
- claim the request was HTTPS, which affects redirects and `Secure` cookie decisions.

This snippet is common in container and cloud guides because it makes forwarded headers "just work". The [proxy documentation](https://learn.microsoft.com/aspnet/core/host-and-deploy/proxy-load-balancer) warns against clearing both lists by default.

## How to fix

Trust the proxy you have:

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.KnownProxies.Add(IPAddress.Parse("10.0.0.100"));
    // or a narrow network: o.KnownIPNetworks.Add(System.Net.IPNetwork.Parse("10.0.0.0/24"));
});
```

## When to suppress

When the network already guarantees that only your proxy can reach the app, for example a Unix domain socket or named pipe with restricted access, or a container that accepts traffic only from the ingress. Write down which one in the justification.

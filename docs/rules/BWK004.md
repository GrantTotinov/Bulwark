# BWK004: MVC action accepts unsafe requests without antiforgery validation

| | |
|---|---|
| Category | Security |
| Severity | Warning |
| Weakness | [CWE-352](https://cwe.mitre.org/data/definitions/352.html): Cross-site request forgery |
| Benchmark | [R03](https://github.com/GrantTotinov/aspnetcore-security-bench/tree/main/rules/R03-mvc-missing-antiforgery) |

## Cause

A public action on a controller that derives from `Controller` handles POST, PUT, PATCH or DELETE (`[HttpPost]`, `[HttpPut]`, `[HttpPatch]`, `[HttpDelete]`, `[AcceptVerbs(...)]`), and no antiforgery filter applies to it:

- no `[ValidateAntiForgeryToken]`, `[AutoValidateAntiforgeryToken]`, `[IgnoreAntiforgeryToken]` or `[RequireAntiforgeryToken]` on the action, the controller or a base class;
- no antiforgery filter added to `MvcOptions.Filters` anywhere in the project.

Controllers with `[ApiController]` (on the class or the assembly) and controllers that derive only from `ControllerBase` are not checked.

## Why it matters

Razor Pages and minimal APIs that bind forms validate antiforgery tokens by default. MVC controllers do not: they validate only where a filter asks for it. A state-changing action without the filter accepts a cross-site form post with the user's cookie.

The built-in rule [CA5391](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca5391) and CodeQL's `cs/web/missing-token-validation` report this only when the project already uses an antiforgery attribute somewhere, so an MVC app with no protection at all gets no warning from them. BWK004 reports it.

## How to fix

Add the global filter that the [ASP.NET Core CSRF docs](https://learn.microsoft.com/aspnet/core/security/anti-request-forgery) recommend for apps with views:

```csharp
builder.Services.AddControllersWithViews(options =>
    options.Filters.Add(new AutoValidateAntiforgeryTokenAttribute()));
```

It validates every POST, PUT, PATCH and DELETE action, including ones added later. `[ValidateAntiForgeryToken]` on a controller or action also works.

## When to suppress

For endpoints that never receive cookie-authenticated requests, such as APIs that use only bearer tokens, mark the controller `[ApiController]` or the action `[IgnoreAntiforgeryToken]` instead of suppressing. That documents the decision in code.

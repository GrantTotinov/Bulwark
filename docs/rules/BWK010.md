# BWK010: Error details are exposed outside Development

| | |
|---|---|
| Category | Security |
| Severity | Warning |
| Weakness | [CWE-209](https://cwe.mitre.org/data/definitions/209.html): Generation of error message containing sensitive information |

## Cause

Outside an `IsDevelopment()` (or `IsEnvironment("Development")`) check, the app:

- calls `UseDeveloperExceptionPage()`, or the EF Core `UseDatabaseErrorPage()` or `UseMigrationsEndPoint()`;
- sets `DetailedErrors = true` on Blazor Server circuit options;
- sets `EnableDetailedErrors = true` on SignalR hub options.

The `else` branch of `if (!env.IsDevelopment())` counts as development.

## Why it matters

These features send exception messages and stack traces to the client: SQL, file paths, type names and sometimes configuration values. That helps an attacker map the app and its database. `UseMigrationsEndPoint()` also lets a client apply pending EF Core migrations.

Since .NET 6, `WebApplication` already shows the developer exception page in the Development environment, so an unconditional call adds nothing during development and only leaks in production.

## How to fix

```csharp
// Before
app.UseDeveloperExceptionPage();
builder.Services.AddSignalR(o => o.EnableDetailedErrors = true);

// After
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/error");
}

builder.Services.AddSignalR(o => o.EnableDetailedErrors = builder.Environment.IsDevelopment());
```

## When to suppress

For an internal tool where every user may see stack traces. Even then, consider logging the details instead.

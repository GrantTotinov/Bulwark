# BWK002: UseRateLimiter() runs before UseRouting()

| | |
|---|---|
| Category | Security |
| Severity | Warning |
| Weakness | [CWE-307](https://cwe.mitre.org/data/definitions/307.html): Improper restriction of excessive authentication attempts |
| Benchmark | [R02](https://github.com/GrantTotinov/aspnetcore-security-bench/tree/main/rules/R02-rate-limiter-before-routing) |

## Cause

`UseRateLimiter()` is called before an explicit `UseRouting()` on the same app, and the project uses endpoint rate limiting policies: `RequireRateLimiting(...)` or `[EnableRateLimiting]`.

## Why it matters

The rate limiting middleware finds an endpoint's policy in the metadata of the selected endpoint. Before `UseRouting()`, no endpoint is selected, so the policy is never applied. A login endpoint limited to 3 attempts per minute accepts every attempt. The app starts normally, throws nothing and logs nothing.

The [rate limiting docs](https://learn.microsoft.com/aspnet/core/performance/rate-limit) say: "`UseRateLimiter` must be called after `UseRouting` when rate limiting endpoint specific APIs are used."

## How to fix

```csharp
// Before
app.UseRateLimiter();
app.UseRouting();

// After
app.UseRouting();
app.UseRateLimiter();
```

If you do not call `UseRouting()` yourself, `WebApplication` adds it at the start of the pipeline and the order is already right.

## When to suppress

Not needed for global limiters: a project with only `options.GlobalLimiter` is not reported, because global limiters work before routing. Suppress if the endpoint policies belong to a different pipeline than the one the rule reports.

## Limits

The rule compares calls within one method, in source order, on the same app variable. Pipelines split across helper methods are not followed.
